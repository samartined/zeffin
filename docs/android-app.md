# Android app: build, signing and releases

## What the APK is

The APK is the **Zeffin** app in `android/` (Kotlin + Compose, Android 14 or later, application id `dev.zeffin`). It does two things:

- **Relay** between the Flipper (Bluetooth) and the server (`/phone`). How it shares the Flipper's link with the server is in [protocol/rpc/](protocol/rpc/README.md), and its layers in [architecture.md](architecture.md).
- **App**: the live Flipper screen, pausing and resuming the agent, its actions, the chat with Claude Code (conversations, permissions, attachments), relay and server state, diagnostics and log (`/app`).

From 1.0.0 on, the app and the server share one version number: app 1.0.0 goes with server 1.0.0. The app's Server settings show the server's version. If the server is too old (`GET /phone/check` answers 404), the app says "The server answers, but it is too old: zf update". A server without the chat (no `"chat"` in `hello.features`) keeps working; a conversation then says the chat needs `zf update`.

Modules: `app` (screens), `relay` (the relay and its service) and `core` (settings, the pairing record with the address and both tokens, encrypted with the Android Keystore, address rules and the pairing QR code, the private network and `ServerHttp`, the only place that sends to the server; see "The private network (Tailscale)"). Third-party licenses are in [android/licenses/THIRD_PARTY_NOTICES.md](../android/licenses/THIRD_PARTY_NOTICES.md) and the app shows them in About.

The app is in English and Spanish. It follows the phone's language; you can change it in Settings, Language.

The *Release APK* workflow (`.github/workflows/release-apk.yml`) publishes each version by itself on GitHub Actions (see "Publish a version"). When Actions cannot run, for example with no minutes left, its run fails without spending any, and `android/scripts/release-apk.sh` builds and signs the same APK, so a release never waits on Actions. The script runs on any machine with JDK 21, the Android SDK and the release key in its environment. It:

1. Takes `--rc` (a candidate, from `release/<fb.version>`) or `--final` (the release, from `main`), and checks that the branch matches `fb.version` in `android/gradle.properties`.
2. Refuses a working tree with changes, or a commit that is not the branch's on GitHub: the APK is that commit.
3. Picks the tag: `apk-v<version>-rc.<n>` with the next free `n`, or `apk-v<version>`. It refuses if `apk-v<version>` already exists.
4. Checks that `android/gradle/wrapper/gradle-wrapper.jar` has Gradle's published hash for the pinned version (the wrapper also checks the distribution's).
5. Builds the release variant, which is not debuggable. The tests ran locally on the branch (CLAUDE.md, "Checks before pushing") and, when Actions can run, in *Tests* on the release pull request.
6. Signs it with the key from the environment, never from the repo, and refuses it if it came out debuggable or if its certificate is not the stable key's.
7. Writes `zeffin-v<version>.apk`, its SHA-256 and the release notes to `android/app/build/outputs/release/`, and prints how to publish them. The notes come from `android/scripts/release-notes.py`, as in the workflow (see "Release notes").

The workflow makes the same checks except the first two, and publishes the release itself.

### Release notes

Every release's GitHub description is generated by one builder, `android/scripts/release-notes.py`, which the workflow and `release-apk.sh` both call, so they never drift:
1. **What's new:** `docs/release-notes/<version>.md`, written by the maintainer on `release/<version>` and brought up to date with each fix (CLAUDE.md, "Branches and versions"). It starts with "## What's new since <previous version>" and holds no commit, hash or certificate.
2. **For a candidate,** the paragraph that says it is one.
3. **"## The APK":** the source commit, how to install it, the APK's SHA-256, the signing certificate's SHA-256 and the key, all generated.

- **A release without its file fails** before anything is built or tagged, naming the file, in the workflow and in `release-apk.sh --final`.
- **A candidate without it** is published with "What's new: not written yet (docs/release-notes/<version>.md)", and the workflow shows a warning.
- To check that a version's file is there before releasing: `python3 -I android/scripts/release-notes.py --check --version X.Y.Z --kind final`.

## Why it must be signed

- Android does not install an unsigned APK.
- You do not need Google: your own key works.
- Android only installs an update on top of the app if it is signed with the **same key**. With another key you must uninstall first and pair again.
- Whoever has the key can publish versions your phone accepts as updates. That is why the key is yours and lives only in your backup and in this repo's secrets.

## Create the key (once)

The key is a standalone file. You do not need this repo cloned. You need Java's `keytool` (any JDK or JRE 17 or later).

On your computer, in a folder of your choice:

```bash
keytool -genkeypair -keystore flipper-bridge.jks -storetype PKCS12 \
  -alias flipper-bridge -keyalg RSA -keysize 3072 -validity 10000 -dname "CN=Zeffin"
```

It asks for a password twice, at least 6 characters. It is not shown as you type.

Then turn the key into text:

```bash
base64 -w0 flipper-bridge.jks; echo        # on macOS: base64 -i flipper-bridge.jks
```

On Windows PowerShell, this copies the same text to the clipboard:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("$PWD\flipper-bridge.jks")) | Set-Clipboard
```

### Store it where releases are built

**On the machine that builds with `release-apk.sh`,** as two environment variables with the names below. Never paste the key or its password into a chat, an issue or a log.

**On GitHub,** for the *Release APK* workflow when it is run by hand: in `https://github.com/samartined/zeffin`, open **Settings**, then **Secrets and variables**, then **Actions**, and create with **New repository secret**:

| Name | Secret |
|---|---|
| `ANDROID_KEYSTORE_B64` | The key text from above |
| `ANDROID_KEYSTORE_PASSWORD` | The password |

Keep `flipper-bridge.jks` and its password somewhere safe off the computer, for example in your password manager. If the folder syncs to a cloud drive, delete it once you have the backup.

## Publish a version

`main` holds what is released (CLAUDE.md, "Branches and versions"): merging a pull request into `main` with a new `fb.version` publishes it. In about 10 minutes the release `apk-vX.Y.Z` appears on the *Releases* page.

**Release candidates.** Each push to a release branch `release/X.Y.Z` (its name must match `fb.version`) publishes a GitHub pre-release `apk-vX.Y.Z-rc.N`, the next N:
- it is the same release build, signed with the same key, so the maintainer tries the binary that ships;
- its version name ends in `-rc.N`, and its version code is the release's;
- it installs over the released app, and the final `apk-vX.Y.Z` installs over it;
- going back to an earlier version means uninstalling first, and pairing again;
- it is marked as a pre-release, so it never shows as the latest release;
- once `apk-vX.Y.Z` exists, the branch publishes no more candidates.
- its description is the generated notes: the version's "What's new" as it stands on the branch, then the candidate's paragraph and the APK's part ("Release notes").

By hand, for example to publish again after a failed run: **Actions** tab, **Release APK** workflow, **Run workflow**, with the version from `fb.version` (for example `1.0.0`). Pushing an `apk-v*` tag also starts it. Check that the release notes say the APK was signed with the repository's stable key; if they mention a one-off key, the workflow did not find the secrets.

**When Actions cannot run** (the run fails in seconds, without spending minutes):
1. Check the *Releases* page first: if the release or candidate is already there, nothing else is done.
2. Run `android/scripts/release-apk.sh --final` on `main`, or `--rc` on the release branch. It writes the APK, its `.sha256` and the notes (`<tag>-notes.md`). `--final` stops before building when `docs/release-notes/<version>.md` is missing.
3. The maintainer publishes them: on GitHub, **Releases**, **Draft a new release**; the tag the script printed (created on publish), with `main` or the release branch as target; title `Zeffin X.Y.Z` (or `X.Y.Z-rc.N`); the generated notes file, unchanged, as the description (never a description of one's own); the APK and its `.sha256` as files; **Set as a pre-release** for a candidate; **Publish release**.
- The script counts the candidates already published, so each one is published before the next is built. It refuses once `apk-vX.Y.Z` exists.

## Install and update on the phone

1. On the phone's browser, open `https://github.com/samartined/zeffin/releases`.
2. Download `zeffin-vX.Y.Z.apk` and open it.
3. Accept "allow installing apps from this source" when Android asks. Play Protect may warn that the app is unknown: that is normal for an app that does not come from Google Play.

Later versions signed with the same key install on top and keep the settings and tokens.

### Test builds (Zeffin Test)

For quick tests on the phone there is a second app, `dev.zeffin.test` ("Zeffin Test"), built with `./gradlew :app:assemblePreview` (`app/build/outputs/apk/preview/app-preview.apk`) and signed with a key only for it, which is not in the repo (below). It installs beside the released app, keeps its own settings and pairing, and each new test APK installs on top of the previous one. Stop the relay in one app before using the other's: both would take the same Flipper. Only the test app writes an RPC timing line per frame from the server in the relay log ("RPC: 24 B written to BLE in 12 ms · from the Flipper: +95 ms 6 B, +410 ms 6 B, +720 ms 6 B · 3 larger chunks, 1038 B (screen, files)": small chunks are RPC replies, listed one by one; larger ones are only counted), to measure the Bluetooth side.

Test APKs come from several branches. Their version code is the minutes from 2026-01-01 to the commit, not `fb.version`, so the newest commit always installs on top, whatever version its branch carries; an older one is refused by Android until the test app is uninstalled. A task's builds say which task they come from: `./gradlew :app:assemblePreview -Pfb.testLabel=ux` gives `<fb.version>-test.ux+1df220c`, for example `1.0.0-test.ux+1df220c` (1 to 12 lowercase letters or digits).

**The test app's key** stays out of the repository, so nobody with a clone can sign a test app:
- **Where it lives:** outside the repo. A build reads two environment variables:
  - `FB_PREVIEW_KEYSTORE_B64`: the keystore (PKCS12, alias `preview`) in base64;
  - `FB_PREVIEW_KEYSTORE_PASSWORD`: the password of the store and of the key.
- **Without them,** only `assemblePreview` fails, and it says why. The tests, lint and the release build need neither.
- **Keep the file safe,** like the release key's. Losing it means uninstalling the test app once. Never paste the key or its password into a chat.

To make a new key, on your computer or the server (never in a chat). With a JDK's `keytool`:

```bash
keytool -genkeypair -keystore preview.jks -storetype PKCS12 -alias preview -keyalg RSA -keysize 4096 -validity 10000 -dname "CN=Zeffin Test"
base64 -w0 preview.jks > preview.jks.b64
```

Or without a JDK, with `openssl`:

```bash
openssl req -x509 -newkey rsa:4096 -days 10000 -noenc -subj "/CN=Zeffin Test" -keyout preview.key -out preview.crt
openssl pkcs12 -export -inkey preview.key -in preview.crt -name preview -out preview.jks
rm preview.key preview.crt
base64 -w0 preview.jks > preview.jks.b64
```

On Windows, PowerShell has no `base64`. Make the text file this way instead:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes((Resolve-Path .\preview.jks))) | Set-Content -NoNewline -Encoding ascii .\preview.jks.b64
```

Do not use `certutil -encode`: it adds header lines that spoil the key. If you copy the text from a terminal and it breaks into several lines, that is fine: the build ignores line breaks.

Then:
1. Both ask for the password. Type it there, so it never stays in the shell history.
2. Put the content of `preview.jks.b64` in `FB_PREVIEW_KEYSTORE_B64` and the password in `FB_PREVIEW_KEYSTORE_PASSWORD`.
3. Delete `preview.jks.b64` and keep `preview.jks`.

A new key cannot update a test app signed with another one: uninstall Zeffin Test once, install the new test APK, and pair it again.

### First setup

1. Show the pairing QR code ([the user's guide](guide/pair-the-app.md#3-pair-the-app-with-the-server)): **Pair the app** in the web view, or `zf pair` on the server. Its code changes every 30 seconds, and the pairing stops after 3 minutes.
2. On the phone, in the app: Settings, Server, **Pair with QR code**, and point the camera at it. On the phone itself, without a second screen: copy the pairing text from the web view or from `zf pair` (in an SSH app) and use "Paste the pairing text". If the phone is already paired with another server, the app asks first: "Keep the current pairing" leaves it as it was.
   - The app checks the server's key against the pin in the QR code before it sends anything, and shows the key's fingerprint.
   - The phone and the server then show the same six-digit number. Confirm on the server only if it is the one on the phone; if the phone shows no number, refuse. The tokens leave only after you confirm.
3. Pair the Flipper in Android's Bluetooth settings if it is not paired yet. In the app: Settings, Relay, **Device**, and choose your Flipper.
4. Turn on the relay switch. Accept the nearby devices and notifications permissions, and turn off battery optimization when the app suggests it.

### The private network (Tailscale)

The app sends a token, a pairing code or the chat to an `http://` or `ws://` address only through Tailscale's tunnel:

- The address must be a Tailscale IP (`100.64.0.0/10` or `fd7a:115c:a1e0::/48`); any other address needs `https://` or `wss://`.
- Each connection goes through the VPN network Tailscale brings up on the phone, and only through a route of it inside those ranges. A VPN that takes all the traffic (a default route) does not count.
- With Tailscale off or reconnecting there is no such route: the app refuses before it opens a socket, so nothing reaches the network, and it says "Tailscale is not connected on this phone" in Home, the conversation, Relay and Pair. Relay's banner shows the cause (no VPN, or a VPN whose routes do not reach the server). Pairing keeps the code unused: try again once Tailscale is on.
- As soon as the tunnel is back, the relay and the app connect again by themselves.
- The app never uses an HTTP proxy for the server, even if the Wi-Fi or a VPN sets one.

Tip, on the phone: Settings, Network, VPN, Tailscale, turn on **Always-on VPN** and **Block connections without VPN**. Then the tunnel comes up by itself, and no other app sends anything outside it either.

What the tunnel does not prove: that whoever answers at the server's address is your server. Any VPN app you install that claims Tailscale's ranges is taken as the tunnel. Authenticating the server (a pinned key) is a later phase.

### The server's key (0.8.0)

The server proves its key to the app (the contract is [protocol/pairing/](protocol/pairing/README.md)).
- **The server speaks only TLS 1.3 on port 9434,** with a key `zf` made: `/phone`, `/app`, `/view` and pairing all go over `https://` and `wss://`.
- **The app pins that key** from the pairing QR code. A server with another key is a hard error, "The server's key changed. Pair again.", and nothing is sent.
- **The server and the app of 0.8.0 go together:** an app of 0.7.0 gets a closed connection from the new server, with no explanation, and the new app reads only the new QR code. Update both, then pair again.
- **After `zf key new` on the server,** pair again. Its fingerprint is in `zf status` and in Settings.

### Check the APK (optional)

Download the APK on your computer and compare its hash with the SHA-256 in the release notes.

```bash
sha256sum zeffin-v1.0.0.apk
```

```powershell
Get-FileHash .\zeffin-v1.0.0.apk -Algorithm SHA256
```

The **signing certificate SHA-256** in the release notes must be the same in every release. If it changes, the key has changed.

### Notification channels

What Android lists in the app's notification settings (Apps, Zeffin, Notifications), where each one can be changed:

| Channel | Importance | What |
|---|---|---|
| Zeffin relay (`relay`) | Low | The relay's state and Stop, while it runs |
| Agent working (`agent_working`) | Low | "The agent is working", while a turn runs with the app off screen (the `remoteMessaging` foreground service) |
| Turn finished (`agent_turns`) | Default | A turn finished, stopped or failed: sound and an icon, no pop-up |
| Permission requests (`agent_permissions`) | High | The agent asks for permission: it pops up, with Allow once (asks to unlock) and Deny |

## If you lose the key

- The installed app keeps working.
- To publish new versions, create another key and replace the two secrets.
- The first install with the new key requires uninstalling the app and pairing again.

## Changing the app

1. Make the changes in `android/`. User-visible texts go in both languages.
2. `fb.version` in `android/gradle.properties` is set only on the release branch (CLAUDE.md, "Branches and versions"); `versionCode` is derived from it (0.1.0 → 100). Android does not install a version with a lower `versionCode` on top of the installed one.
3. **Without the Android SDK** (a machine with JDK 21 only), install it first. Keep `android/local.properties` untracked:
   ```bash
   curl -sS -o /tmp/cmdtools.zip https://dl.google.com/android/repository/commandlinetools-linux-11076708_latest.zip
   mkdir -p ~/android-sdk/cmdline-tools && unzip -q /tmp/cmdtools.zip -d /tmp/ct && mv /tmp/ct/cmdline-tools ~/android-sdk/cmdline-tools/latest
   export ANDROID_HOME=~/android-sdk; yes | ~/android-sdk/cmdline-tools/latest/bin/sdkmanager --licenses >/dev/null
   ~/android-sdk/cmdline-tools/latest/bin/sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.0.0" "platforms;android-37.0"
   echo "sdk.dir=$HOME/android-sdk" > android/local.properties
   ```
4. Before pushing: `cd android && ./gradlew testDebugUnitTest lintDebug detekt :app:assembleRelease` (JDK 21) and, from the root, `.venv/bin/python -I android/scripts/compare-design-captures.py` and `PYTHON=$PWD/.venv/bin/python android/scripts/e2e.sh`.
5. Open a pull request to `dev`. The *Tests* workflow runs the same checks on its merge with `dev` when it is not a draft (CLAUDE.md, "Checks before pushing"), and by hand (Actions, Tests, Run workflow).
6. Screenshots of each screen land in `android/app/build/outputs/roborazzi/en` and `…/es`. `compare-design-captures.py` fails when an English one differs from its capture in `docs/design/captures/` and marks the changed pixels in `android/app/build/outputs/design-compare/`. When the maintainer approves a screen change, `android/scripts/update-design-captures.sh` copies the English ones there.
7. When `dev` is checked on a phone, the maintainer releases it through a pull request from `release/<version>` to `main`, which publishes the version as described above.

If you change the Gradle version, also update `GRADLE_WRAPPER_SHA256` in both workflows and in `android/scripts/release-apk.sh`.
